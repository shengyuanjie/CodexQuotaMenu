# Scriptable 小组件刷新优化设计

## 目标

在不付费、不制作原生 iOS App、不改变 Mac 服务端的前提下，尽量缩短 Scriptable 锁屏小组件的自动刷新等待时间，并提供用户可主动触发的刷新兜底和可核对的实际刷新记录。

正常显示文案保持不变：

```text
剩82% 余6天 Tibo23%
```

## 平台边界

- `ListWidget.refreshAfterDate` 只表示允许再次刷新的最早时间，iOS 不保证按指定时间执行。
- 自动刷新目标是每 5 分钟申请一次，这是本方案的最小目标间隔，不宣称固定 5 分钟刷新。
- 点击刷新会打开 Scriptable。请求完成后系统何时重绘锁屏组件仍需 iPhone 实机验证。
- 不使用低于 5 分钟的循环、快捷指令伪定时、推送服务或需要重新签名的原生 App。

## 交互与运行模式

脚本根据运行环境和小组件参数选择行为：

- 小组件后台运行：直接请求 Mac 接口、更新缓存、生成组件，并将下一次最早刷新时间设为 5 分钟后。
- 点击小组件运行：当参数为 `refresh` 时，跳过配置窗口，立即请求 Mac 接口、更新缓存并重新生成组件；请求完成后在 Scriptable 中显示简短结果，明确区分实时成功和缓存兜底。
- 手动从 Scriptable 运行：没有 `refresh` 参数时，保留现有地址和访问令牌配置流程。

iPhone 小组件设置固定为：

```text
Script: CodexQuotaWidget
When Interacting: Run Script
Parameter: refresh
```

## 刷新诊断记录

每次脚本完成数据加载后，在 Scriptable 本地 Documents 目录写入不含敏感信息的诊断记录。每条记录包含：

- 完成时间；
- 运行模式：后台小组件、点击刷新或手动运行；
- 数据来源：实时或缓存；
- 请求结果：成功或错误分类；
- HTTP 状态码（存在时）；
- 本次加载耗时毫秒数。

记录最多保留最近 3 天且不超过 200 条。日志不得包含访问令牌、完整请求头或接口响应正文。缓存继续使用现有文件和两小时过期规则。

## 组件与数据流

保持单文件 Scriptable 结构，避免为手机端引入模块加载和同步复杂度。新增或调整以下纯逻辑边界：

- `resolveRunMode(...)`：根据 `config` 和 `args.widgetParameter` 返回运行模式。
- `nextRefreshDate(now)`：生成 5 分钟后的最早刷新时间。
- `appendRefreshDiagnostic(...)`：追加、裁剪并保存安全诊断记录。
- 点击刷新结果提示：使用已经格式化的当前数据，不暴露凭据。

数据流如下：运行模式判定 → 读取 Keychain 凭据 → 实时请求或缓存兜底 → 写入缓存和诊断记录 → 构建现有单行/矩形组件 → 设置下一次最早刷新时间 → 交给 Scriptable。

## 错误处理

- 无凭据时仍显示配置提示；点击刷新模式下提示用户先手动运行脚本完成配置。
- 实时请求失败时继续沿用现有缓存策略。两小时内缓存可显示，超过两小时不展示旧数值。
- 后台小组件运行不弹窗；点击刷新和手动运行可以显示简短错误说明。
- 诊断日志写入失败不得阻断有效数据或组件渲染。

## 测试与验收

自动化测试覆盖：

- 5 分钟最早刷新时间的计算；
- `refresh` 参数正确进入点击模式，普通手动运行仍进入配置模式；
- 诊断记录只保留 3 天内最多 200 条；
- 诊断记录不包含访问令牌和响应正文；
- 现有 schema v2、缓存过期和单行文案测试继续通过。

Mac 端可执行验证包括语法检查、完整测试、工作副本与交付副本一致性检查。iPhone 最终验收必须由用户完成：

1. 手动运行脚本仍可进入配置；
2. 将参数设为 `refresh` 后点击锁屏组件能够打开 Scriptable 并发起实时请求；
3. 返回锁屏后观察是否在数秒内重绘；
4. 保持至少 24 小时后导出或查看诊断记录，统计实际后台刷新间隔；
5. 分别在家庭 Wi-Fi 和蜂窝网络加 Shadowrocket 回家链路下验证。

只有第 2 项可以由点击行为保证立即请求；第 3、4 项受 iOS 调度影响，不能在 Mac 端提前宣称成功。
