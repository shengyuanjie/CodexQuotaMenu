# CodexQuotaMenu 无记录激活与预测源迁移设计

日期：2026-09-04  
目标版本：v1.6.7

## 1. 目标

本次变更同时解决三个用户可见问题：

1. 每日激活不再使用 Codex standalone cron，避免每次运行都在“最近任务”中创建新的对话记录。
2. 全局额外重置预测改为 `https://willcodexreset.com/api/reset-radar`。
3. `冲冲冲～使劲蹬啊～` 改为在一轮预测中首次达到 50% 及以上时显示。

同时修正激活时间开关语义：关闭保留该时间但停止调度，删除才移除该时间。

## 2. 非目标

- 不自动清理或归档用户已有的普通 Codex 最近任务。
- 不把新激活任务继续展示在 Codex“已安排”中。
- 不解析或展示 Will Codex Reset 的事件、帖子、用户数、里程碑或广告数据。
- 不改变 Codex 个人 5 小时/每周用量读取逻辑。
- 不在本次变更中自动发布 GitHub Release。

## 3. 无记录激活架构

### 3.1 执行方式

每个启用时间由一个用户级 macOS LaunchAgent 调用本机已安装的官方 Codex CLI：

```text
codex exec --ephemeral --ignore-user-config --ignore-rules \
  --skip-git-repo-check --sandbox read-only \
  --model gpt-5.6-luna --cd <用户主目录> \
  <最小激活提示词>
```

`--ephemeral` 是关键约束：调用仍使用当前 Codex 登录执行一次模型请求，但不把会话持久化为最近任务。标准输出和标准错误写入 `/dev/null`，成功运行保持静默。

应用沿用现有 Codex 可执行文件候选顺序，并在应用设置时把解析到的绝对路径写入 LaunchAgent。找不到可执行文件时拒绝同步，不留下半配置状态。
同步前还要读取 `codex exec --help`，确认当前 CLI 支持 `--ephemeral`、`--ignore-user-config` 和 `--ignore-rules`；缺少任一安全参数时拒绝迁移，继续保留旧任务。

### 3.2 所有权

应用只管理以下精确标签和文件名：

```text
com.local.codexquotamenu.activation.HHMM
~/Library/LaunchAgents/com.local.codexquotamenu.activation.HHMM.plist
```

`HH` 必须为 00–23，`MM` 必须为 00–59。仅共享前缀但不完整匹配的 LaunchAgent 不属于应用，必须保持不变。

每个启用时间对应一个已加载 LaunchAgent，使用 `StartCalendarInterval` 的小时和分钟字段。关闭的时间仍保存在 `UserDefaults`，但不保留或加载对应 LaunchAgent；重新开启并应用时按同一稳定标签恢复。删除时间同样移除对应 LaunchAgent，但还会从本地设置列表删除该条目。

### 3.3 应用与状态检测

继续保留“应用到 Codex”按钮作为唯一写入入口，切换开关或编辑时间只保存本地设置并显示待应用状态。

同步时：

1. 读取并验证现有受管 LaunchAgent 与旧版 `CodexQuotaMenu · HH:mm` Codex automation。
2. 在临时目录生成并验证全部目标 plist。
3. 备份现有受管 plist，卸载旧受管 LaunchAgent，原子替换文件并加载全部启用项。
4. 用 plist 内容和 `launchctl` 实际加载状态共同验证结果。
5. 只有新调度完整可用后，才删除旧版严格受管的 Codex standalone cron。
6. 任一步失败都撤销本轮 LaunchAgent 变更；若无法验证恢复，保留明确标记的恢复副本并停止后续同步。

状态自动检测继续在窗口打开、获得焦点及可见期间定时执行。`synced` 要求每个启用时间恰好有一个配置正确且已加载的 LaunchAgent，关闭时间没有已加载任务，也不存在多余的严格受管任务。检测失败显示不可用，不能猜测为已同步。

首次从 v1.6.6 应用时会迁移并移除旧版严格命名的 Codex automation，因此之后不再在 Codex“已安排”中显示这些激活任务。其他 Codex automation 不受影响。

### 3.4 macOS 行为

LaunchAgent 属于当前登录用户，注销时不运行。`StartCalendarInterval` 遇到 Mac 睡眠时遵循 macOS 的合并触发语义，唤醒后可能补执行一次；应用不自行实现额外补偿或多次追赶。

## 4. Will Codex Reset 数据源

### 4.1 请求与字段

唯一预测请求改为：

```text
GET https://willcodexreset.com/api/reset-radar
```

只接受以下必要结构：

```json
{
  "code": 0,
  "data": {
    "updatedAt": "2026-09-04T02:42:22.950Z",
    "probability48h": 99
  }
}
```

要求 HTTP 2xx、`code == 0`、`updatedAt` 为合法 ISO-8601 时间、`probability48h` 为 0...100 的整数。显示更新时间采用来源的 `updatedAt`；本地获取时间只用于缓存年龄和故障回退判断。

内部模型分别保存来源更新时间和本地获取时间，不能用来源时间代替缓存年龄，也不能把本地获取时间冒充来源更新时间。

### 4.2 有界读取

接口当前还附带数百 KB 的事件日志。客户端不需要这些数据，也不能无界下载。接收器最多保留 64 KiB 前缀，在确认顶层预测摘要完整并到达 `events` 数组边界后构造仅含必要字段的内部响应并主动停止传输。如果必要字段在上限内未完整出现、字段重复或结构不符合预期，则本次刷新失败并沿用现有的安全缓存回退。

请求仍使用短超时、无 Cookie、无凭据存储、无 URL 缓存的临时会话。应用不向来源发送个人余量、任务、身份、会话或 Codex 凭据。

### 4.3 缓存和对外数据

预测缓存键升级到 v3，忽略但不删除旧来源的 v2 缓存，防止旧值被误标为新来源。菜单、README、隐私说明和手机只读 JSON 中的来源统一改为 `willcodexreset.com`；手机 JSON 架构版本在字段结构不变的前提下保持兼容，只替换来源字符串。

## 5. 50% 首次触发规则

阈值统一定义为 50：

- 概率从无值或低于 50% 首次进入 `>= 50%` 时显示 `冲冲冲～使劲蹬啊～`。
- 概率持续处于 `>= 50%` 时，不因普通刷新重复开始新一轮。
- 检测到重置完成后，在本轮高概率周期余下时间保持隐藏。
- 概率降到 50% 以下后重新布防；下一次进入 `>= 50%` 再显示。
- 来源暂时不可用时保持原状态，不错误重新布防。

庆祝状态键升级到 v2。旧来源的 v1 状态不迁移，确保迁移后新来源第一次返回 `>= 50%` 时能够显示。菜单栏和手机小组件继续使用同一个状态决策。

## 6. 测试与验收

实现采用测试驱动方式，至少覆盖：

- LaunchAgent plist 的标签、日程、Codex 路径和 `--ephemeral` 参数完全正确。
- 启用、关闭、删除三种语义互不混淆。
- 状态检测同时核对文件配置与实际加载状态。
- 首次迁移只删除严格命名的旧 Codex automation，不触碰其他任务。
- 同步失败回滚、并发碰撞和不可验证恢复路径。
- 运行命令使用可替换的假 Codex 可执行文件，自动测试不实际消耗用户用量。
- 新预测响应的成功解析、非 2xx、错误 code、缺失/重复字段、越界概率、非法时间和超过前缀上限。
- 预测客户端不会接收或缓存 `events` 内容。
- 49% 不显示、首次 50% 显示、持续高位不重复、跌破后重新触发、重置后同轮隐藏。
- 新缓存和状态键不会读取旧来源数据。
- 全量 Swift 测试、arm64 Release 构建、签名、压缩包和架构审计通过。

安装后的人工验收只检查配置和状态，不主动执行真实的 Codex 激活请求；实际到点运行后由用户确认最近任务列表没有新增记录。
